## Everyday editing

1. Choose a character or create a new one. Search by name, or filter the cast by Development post, Encyclopaedia details, Directory details, or Updates to review. A character opened from the cast browser is selected automatically.
2. Edit the labelled fields. Add connections, songs and story entries with the corresponding buttons.
   In Photos, colour & place, replace the header photo and its colours will be matched automatically. Adjust the crop and add a separate portrait / PI image as needed. Manual colour is an optional override. Use starter appearance restores the supplied header/PI photos while keeping other details.
3. Change the three polaroid names, images and optional links. For a map, enter a city label, use Find a place on OpenStreetMap, then paste the map address into OpenStreetMap link and choose Use this map view. Coordinates and zoom can also be edited directly. Clearing the coordinates hides the map. The pin is a location you set for the character, not live tracking. Ship details and shared stories can be expanded inside their connection card.
4. Copy the forum post and paste it into your Blue Hour development post. The copy includes its `[dohtml]` wrapper, one hosted stylesheet and one shared script for the map and automatic colour matching.
5. Save a library backup regularly. Import that backup on another computer or share it with Sara to continue editing. Backups also remember which supplied details your draft was based on, so later source updates can preserve your changes.

Changes are saved in this browser when storage is available. A backup is a downloadable data file; you do not need to open or edit its contents. Browser saving does **not** publish to GitHub, update the live forum, or synchronise with Sara. Re-copy the forum post after changing its content. To keep a shared version in GitHub, upload the exported backup to the repository; import that same backup before either of you makes the next edit.

## Supplied details and your edits

The small source panel above the form identifies where a character's supplied details came from and links to those sources. Its label describes the available source, not a promise that every section is complete. Missing information stays blank. Source notices and update controls appear only in the editor, never in the copied forum post.

When you open a newer copy of the editor, unchanged supplied fields can receive new source details automatically. Your edited fields, added entries and deliberately removed entries are kept. If both your draft and the source changed the same detail, **Review source updates** shows the two versions side by side. Tick only the changes you want, then choose **Apply selected updates**. **Keep my edits** keeps your current version for every item in that review. Neither option publishes anything to the forum.

Older backups without comparison history are treated cautiously: blank details may be filled, while differing filled details are offered for review. Download a fresh backup after reviewing updates to carry those choices to another browser or to Sara.

## One connected record

Each connection has separate optional Flavour and Brand fields, alongside its relationship type and related story links. A flavour or brand name does not itself establish romance; Partner is recorded separately. Each story entry is added once and can refer to more than one connection. A group connection works alongside individual people. Relationship status is edited once for the profile header; individual connections can retain their own labels and histories. The three polaroids are independently editable photographs and captions.

The dossier brings identity, factual details, inner circle, location, ships and flavours, chronology, soundtrack, and optional continuity notes into one consistent layout. Blank optional sections disappear. Spotify songs retain their real players inside the horizontal carousel, with ordinary listening links as a fallback. A full playlist, if supplied, becomes the last slide. There is no automatic playback or automatic cycling. Legacy trait and pin data is preserved in backups but is no longer displayed.

The timeline uses the **in-world date**, when supplied, and otherwise the **topic start date**. Dates display as **Oct ’26**, or **2026** when only the year is known, and entries sort oldest first beneath year headings. Hovering over a date shows its full value and whether it is a story date or a topic start date. All 305 topics in the imported library have verified start dates from Blue Hour’s topic listings; these are distinct from last-reply dates and the dates the development profiles were created. Existing timeline entries can still be marked as milestones.

Pasting a known topic link in the editor fills its verified start date. Changing that link updates its automatic date; a manually entered date is preserved. For new Blue Hour topics outside the imported list, the posted template can read the first post’s timestamp while you are signed in and viewing or previewing it on Blue Hour. It only reads linked topics on the same forum, never uses a proxy, and never transmits forum pages elsewhere. A local editor cannot access that signed-in forum session, so the new date may first appear in the Blue Hour preview; you can also enter it in the editor’s **Topic start date** field. Unreadable topics remain under **Date Unavailable**, rather than having a date guessed from their topic number.

## GitHub and forum delivery

The layout, editor, starter content and generators live together in `character-dossier/`. Shared forum styling is served from the `character-dossier-v1` branch of `lexdoescodingnow/templates` through jsDelivr. Keep that branch available while posts use its stylesheet URL. The editor has an advanced stylesheet field for a future permanent destination.

The exported profile uses static HTML, one shared stylesheet and one external runtime script. The facts, connections, timeline and song carousel remain readable without that script. The runtime creates the optional map in a separate sandboxed iframe and matches the colour of each header photo. Character colour leads the panels, borders and highlights, with member colours retained for bold/italic text. It follows Blue Hour light/dark mode. The current stylesheet is `dossier-v5.1.css` with the isolated `bh-dossier-v5` wrapper; the earlier v1–v4 stylesheets remain unchanged.

The clean map needs the shared script to load, an internet connection, and browser support for WebGL and Blob workers. Its iframe is created after forum parsing and has `sandbox="allow-scripts"`, without same-origin permission. MapLibre is pinned to the 5.6.2 classic bundle for its self-contained worker; its automatic attribution renderer is disabled and fixed visible credit links are provided below the map instead. Keep user text out of the generated map script and do not enable arbitrary attribution HTML. External location and music links remain available if an embed cannot load.

Automatic colour matching runs both in the editor and in the posted template. Replacing the header URL in either place triggers a new match; the image controls the accent and its related panel tints, borders and highlights. Mostly grey photographs now produce a muted theme, instead of letting a tiny colourful detail dominate. Neutral surfaces also follow the selected accent without a fixed green cast. It does not change the layout or the forum's light/dark setting. A cached accent keeps the post styled while the image is being analysed. Changing the file behind an unchanged URL may be delayed by the image host's cache; a new image URL gives a fresh match.

The current export uses the v5.1 stylesheet and v5.2 runtime. Open the updated editor at the same file location to keep browser drafts; previously sampled automatic colours are recalculated once with the corrected matcher. Manual colour choices are preserved. Copy the post again to use the corrected styling and topic dates in Blue Hour. Temporary colour-sampling failures retry up to twice before retaining the previous colour and reporting the problem in the editor.

Public image hosts such as l3n do not permit direct browser colour sampling. For those images, the matcher uses a small image copy from the [wsrv.nl image cache and resize service](https://wsrv.nl/docs/). Other hosts are sampled directly where possible. Use public image URLs; the fallback excludes local addresses, embedded credentials and common signed or authentication query parameters. If a photo cannot be sampled or the service is unavailable, the previous accent is retained and the editor reports the problem. Automatic matching does not require a manual palette or another assistant request.

The folder is also suitable for [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages), which serves static HTML, CSS and JavaScript. The portable editor is usable without setting up Pages.

## Development

Run `node character-dossier/build.cjs` from the repository root to refresh the enriched library, portable editor, cast browser, all-character ZIP and coverage report. Run `node character-dossier/check.cjs`, `node character-dossier/check-source-updates.cjs`, `node character-dossier/check-migration.cjs`, and `node character-dossier/all-cast-check.cjs` for content preservation, editor updates, source migration and archive validation. Topic dates have additional checks in `check-topic-date-import.cjs`, `check-editor-topic-dates.cjs`, and `check-topic-dates.cjs`; colour recovery is covered by `check-editor-photo-retries.cjs` and `check-photo-runtime.cjs`. The build does not alter existing collections or the PI directory.
